# `progress.md` 最新進度審查與改進建議 (`argon_reply7.md`)

## 一、進度判讀

最新章節（17:25 USBPcap 基準、17:32 突破）：

- **波形已成功渲染**，assert 消失；
  關鍵發現是 Windows 實測裝置每次 bulk IN 的**自然封包 = 405,504 bytes**，helper 改為每次抓 405,504 並累積到 App 要求的長度（`DSW_CHUNK_BYTES` / `DSW_FILL`）。
- **仍未解決**：約 2 個影格後 `LIBUSB_ERROR_STALL`，App 停止；另有標頭 type（Windows `1` vs Wine `2`）與 App 單次要求大小（Windows 405,504 vs Wine 5,005,312）的差異未被解釋。

先確認一件事：已用 `lsusb` 檢查，裝置為 **SuperSpeed 5 Gbps**（`bcdUSB 3.00`，`0x86` maxpacket 1024、burst 3），helper `speed_to_windows` 回傳 3＝Super，與 Windows 端一致，**排除「速度不同」**。

## 二、對目前做法的評論

### 1. 「405,504 + 強制補滿」是繞道，不是根因

- 這個修正讓 App 的 assert 不再觸發，但它是**把 App 的 5 MB 要求拆成 13 次裝置封包再拼起來**。Windows 上 App 並不是這樣運作（URB 即 405,504）。
- 重點問題：**為什麼 Wine 上 App 要求 5,005,312，Windows 上要求/看到 405,504？** 這與標頭 `type 2 vs 1`、控制命令差異是**同一個根因的不同症狀**——App 在兩邊走了不同的設定路徑（模式 / 通道組合 / 緩衝大小）。
- 如果不找出此差異，`DSW_CHUNK_BYTES=405504` 只對「這個預設設定」有效；換取樣率、通道數、模式（Buffer / Stream / 內部測試）裝置的封包大小就會變，硬編碼會再次失效。

**建議**
- 讓 helper **自動學習**封包大小：同一 endpoint 第一次短封包 / ZLP 的長度記為 `learned_chunk`，之後以它為單位；模式切換（偵測到 0xb0 的啟動命令序列或新標頭）時重置。環境變數保留作為覆寫。
- 同時 log 出每個標頭的 `type` 與後續封包大小，建立「模式 → 封包大小」對照表。

### 2. 控制命令差異（相似度 75.7%）很可能是 App 設定不同，而非 shim 錯誤

`Windows: 40 0d 00 / 28 00 04 / 2b 00 00` vs `Wine: 40 05 00 / 28 02 01 / 2b 00 00`。

- shim 對控制傳輸是**原樣轉送**，所以差異必定來自 App 送了不同的值，不是傳輸損毀。
- `0x0400` vs `0x0102/0x0201/0x0300` 看起來像各通道的類比設定／校正偏移（零點 DAC、增益）。同一台硬體卻不同，原因可能是：
  - 兩邊 App 使用不同的**使用者設定 / 校正檔**（Windows 那台錄製時有舊設定）；
  - Wine 這邊讀到的 `MSO ZERO` / 校正資料不同（例如校正資料由 `0xb2` IN 讀回，內容若被截斷或位元組序不同，App 算出的值就不同）；
  - 通道啟用狀態與 vdiv 不同（`type 1/2` 可能代表啟用的通道數或 8-bit/12-bit 模式）。

**建議：做「受控對照」而不是比較兩個不同設定的擷取**
1. 兩邊都用**完全相同、明確寫下的設定**：通道啟用（例如只開 CH0）、time/div、耦合、vdiv、觸發方式、模式；Windows 與 Wine 都清空使用者設定後再套。
2. 把兩邊「Run 按下前」的 **所有 `0xb2` IN 控制傳輸 payload（hex）** 記入日誌並逐筆比對——這些是 App 判斷裝置能力與校正值的來源，是最可能導致分歧的資料。
3. 若 IN payload 一致、設定一致、仍然 type 不同，再往 App 的條件分支查（可能依 OS API 回傳值，例如 `GetVersion`、`libusb` 的 speed / 描述符、記憶體大小）。

### 3. STALL 的優先判斷：多半是「讀取節奏」與「停止流程」，不是硬體壞

觀察：seq4 在 3,244,032（= 8×405,504）bytes 中斷，seq5 直接 STALL。

可能原因與驗證：

| 假說 | 說明 | 驗證 |
|---|---|---|
| **A. 讀取出現空窗導致裝置/FPGA 溢位** | 目前每個封包是**同步的** `libusb_bulk_transfer`，每筆之間經 TCP 往返 + 重新提交，匯流排上短暫無 URB。Windows 上是多個 URB 連續掛著（1964 次幾乎背對背）。裝置 FIFO 滿 → FX3 停止並 STALL | 對照 usbmon / USBPcap 的**相鄰 URB 時間間隔**；在 helper 記錄每次 chunk 之間的 gap（µs） |
| **B. 影格結束後仍有讀取在飛** | 裝置完成一個影格後狀態改變，後續已掛上的 bulk read 命中 STALL；Windows 則由 App 的 abort + `ResetPipe` 清除 | 檢查 STALL 發生前 App 是否送了停止/狀態命令（`0xb0` 序列、`0x84` 讀取）；在 helper log 標出 `stop` 與 STALL 的先後 |
| **C. 停止時 abort 太慢或未實際取消 hardware 端** | `WinUsb_AbortPipe` 只標記，helper 最久 200 ms 才反應；其間可能多讀一次 | 量測 abort→helper 實際返回的延遲 |

**建議（對應 A，優先）**：helper 的 Bulk IN 做**管線化**——對同一 endpoint 維持 **2–4 個**以 `libusb_submit_transfer` 掛著的非同步 URB（每個 405,504 或學到的封包大小），完成一個立刻補一個，資料依序餵給 App 的等待中請求。這樣匯流排上永遠有 URB，行為接近 Windows。
- 這也順便消除之前討論過的「逾時取消可能丟資料」問題（不再使用 200 ms 切片）。
- 取消只在 `REQ_ABORT_PIPE` / 關閉時發生。

**建議（對應 B）**：STALL 時不要直接把錯誤上拋給 App。先對該 endpoint `libusb_clear_halt` 並**重試一次**（Windows 的 WinUSB 在 App 呼叫 `ResetPipe` 時才清除，但若 App 有重試機制，shim 靜默清除並重讀可避免 App 停止）；同時記錄這次 STALL 的上下文，確保不是掩蓋真正的錯誤（只重試一次、並在 log 標示）。

## 三、其他仍需處理或強化的項目

| 項目 | 建議 |
|---|---|
| **`DSW_FILL` 預設開啟的副作用** | 短封包後仍繼續讀，可能把下一影格的標頭併入同一筆完成，造成 App 看到的邊界與裝置不同。建議限制：只在「學到的 chunk 大小倍數」內補滿；遇到 4096 標頭魔數（`55 55 55 55`）時**立即結束**，不跨越影格 |
| **標頭魔數掃描** | helper 已有 `0x55555555` 掃描；把「標頭出現位置 ≠ 讀取起點」當作警告 log，及早發現漂移 |
| **長時間擷取穩定性** | 補壓力測試：連續 Run 5 分鐘、Run/Stop ×20、拔插；記錄 STALL 次數、handle 數、worker 數是否回到基準 |
| **日誌量** | 現有診斷日誌很多（每封包 `head64`/`tail64`、全 word dump）。預設改為摘要，詳細模式用環境變數開啟，避免拖慢熱路徑造成 gap（可能反過來加重假說 A） |
| **自動化回歸** | 把 `parse-usbpcap.py` 的比對流程腳本化：跑完一次擷取輸出「標頭 type、chunk 大小、IN 傳輸數、錯誤數」摘要，與 Windows 基準自動對比 |
| **文件** | `progress.md` 已 532 行且有互相矛盾的舊結論（例如 16:25 的「短封包不結束」）。建議新增一頁「目前有效結論」，舊章節標註已被推翻 |

## 四、建議執行順序

1. 在 helper 加入 chunk 間隔 gap、STALL 前後事件（停止命令、`0x84` 讀取）的時間戳記錄（最便宜，先確認假說 A/B/C）。
2. 記錄並比對「Run 前」所有 `0xb2` IN payload；以**完全相同的設定**重錄 Windows 與 Wine，解釋 type 1/2 與 405,504/5,005,312 的差異。
3. Bulk IN 改為 **2–4 個 URB 的管線化非同步讀取**；STALL 時 `clear_halt` 並單次重試。
4. 封包大小改為自動學習，`DSW_FILL` 加入標頭魔數邊界保護。
5. 壓力測試與回歸腳本。

> [!IMPORTANT]
> 目前「看起來能用」是因為預設設定恰好符合硬編碼的 405,504。真正的驗收條件應是：**不靠環境變數，在多種取樣率/通道組合下，Wine 與 Windows 的標頭 type、讀取大小與錯誤數一致。**
